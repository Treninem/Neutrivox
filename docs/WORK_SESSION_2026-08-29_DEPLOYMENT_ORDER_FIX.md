# Рабочая запись — исправление порядка физической передачи

## Пользовательский запрос
Продолжить разработку.

## Как понята задача
Нужно продолжать непосредственно в репозитории и отдавать предпочтение крупным законченным изменениям. В физическом deployment порядок целей должен быть явным и совпадать с порядком, который пользователь подтвердил в плане.

## Что обнаружено
Предыдущая реализация `DeploymentExecutionService` сортировала `DeploymentTarget` по `ProjectDeviceId`. Это могло изменить порядок, который был сформирован для пользователя в `DeploymentWorkflowService`.

## Почему это проблема
GUID является техническим идентификатором и не имеет пользовательского смысла как порядок загрузки. В промышленном проекте важен явно выбранный порядок: прибор №1, затем №2, затем №3.

## Что сделано
- `DeploymentTarget` получил явное поле `Order`.
- `DeploymentPlan` получил `PlanFingerprint` как метаданные для сохранения отпечатка подготовленного плана.
- `DeploymentExecutionService` больше не сортирует цели по GUID как по основному порядку.
- Исполнение идёт по `DeploymentTarget.Order`, а GUID используется только как детерминированный второй ключ для защиты от неоднозначности.
- Перед выполнением каждой цели проверяется непрерывность порядка `1, 2, 3, ...`.
- При неправильном или пропущенном порядке выполнение останавливается с понятным ошибочным состоянием.
- При отсутствии контекста, подтверждения или adapter выполнение останавливается, чтобы не переходить молча к следующему физическому прибору.
- Итоговый результат содержит фактический номер цели.

## Принцип
Физическая передача остаётся строго последовательной. Успешная загрузка одного прибора не означает автоматическое выполнение следующего, если первый завершился ошибкой.

## Ограничение
Этот блок исправляет порядок execution, но сам по себе не подтверждает совместимость оборудования и не доказывает корректность vendor-протокола. Для этого сохраняются profile matching, preflight, safety gate и production adapter.

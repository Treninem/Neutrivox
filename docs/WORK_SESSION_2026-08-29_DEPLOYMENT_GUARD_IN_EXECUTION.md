# Рабочая запись — интеграция защиты плана непосредственно перед физическим выполнением

## Дата
2026-08-29

## Что сделал
Интегрировал `DeploymentPlanGuardService` и `DeploymentSafetyGateService` непосредственно в `DeploymentExecutionService`.

## Как понял задачу
Физическая передача не должна полагаться только на проверки, выполненные при построении предпросмотра. Между подготовкой плана и нажатием кнопки запуска или между двумя приборами проекта пользователь может изменить проект, привязку или состояние устройства.

Поэтому проверка целостности должна находиться непосредственно в execution path, максимально близко к физическому I/O.

## Почему принято это решение
1. Предварительная проверка сама по себе не защищает от изменений после её выполнения.
2. Fingerprint позволяет недорого обнаружить изменение существенных данных проекта.
3. Повторный safety gate непосредственно перед запуском не позволяет обойти обязательное подтверждение и требования verified adapter.
4. Повторная проверка fingerprint перед каждым отдельным прибором защищает вторую и последующие цели при многоцелевой передаче.
5. Явный `Order` уже является частью `DeploymentTarget`, поэтому выполнение теперь использует именно пользовательский порядок, а не GUID.

## Изменение поведения
Перед началом физического выполнения проверяются:
- непустой план;
- корректная последовательность 1..N;
- соответствие плана текущему проекту;
- наличие fingerprint;
- совпадение fingerprint с текущим проектом;
- safety gate;
- явное подтверждение пользователя;
- наличие проверенного deployment adapter.

Перед каждым следующим физическим target fingerprint проверяется повторно.

При нарушении условий цепочка останавливается, а последующие приборы не запускаются автоматически.

## Ограничения
Fingerprint не доказывает совместимость с конкретной моделью. Для этого остаются профиль оборудования, compatibility checks и verified deployment adapter.

## Проверка
Изменение внесено в `DeploymentExecutionService.cs`. Фактический compile/CI ещё необходимо выполнить и зафиксировать отдельным результатом; наличие изменённого исходника само по себе не считается успешной сборкой.

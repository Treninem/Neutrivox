# Рабочая запись: обнаружение и профили оборудования

## Сообщение пользователя
«далее».

## Как понята задача
Нужно продолжать разработку крупными функциональными блоками. Следующий логичный слой после профилей и сопоставления — реальное обнаружение доступных endpoint'ов, но без выдуманного определения модели по одному IP.

## Что сделано

Добавлены контракты транспортных адаптеров, проверка области сетевого поиска и координатор обнаружения.

В этом блоке добавлено:

1. `EthernetEndpointDiscoveryProvider` — проверка доступности TCP endpoint по явно указанному IP или ограниченной IPv4-подсети.
2. Ограничение параллельных попыток до 32 и ограниченный тайм-аут, чтобы поиск был предсказуемым.
3. `SerialPortInventoryDiscoveryProvider` — перечисление локальных COM-портов без передачи данных.
4. `DiscoveryProviderFactory` — стандартная регистрация discovery providers.
5. `DiscoverySafetyService` — ограничение области автоматического поиска.

## Как это вписывается в существующую систему

Поиск теперь разделён на: проверка области → запуск зарегистрированных провайдеров → получение endpoint'ов → отдельная протокольная идентификация → сопоставление с документированным профилем → явное подтверждение привязки.

## Почему выбран этот вариант

Пользователь требует, чтобы Neutrivox действительно видел подключённые приборы, различал IP-адреса и понимал, что именно подключено. Одной доступности IP недостаточно: IP-адрес не доказывает модель. Поэтому discovery не имеет права автоматически превращать endpoint в конкретный прибор.

Поиск ограничен явно заданной областью. Это делает поведение предсказуемым и предотвращает случайное сканирование произвольных сетей.

## Важное ограничение

TCP-доступность порта ещё не означает, что по нему находится ОВЕН или что устройство поддерживает требуемую операцию. Для этого нужен отдельный протокольный interrogation provider, использующий документированные механизмы.

## Связь с ранее подтверждёнными профилями

В репозитории отдельно зафиксированы документированные варианты ПР100 и профили ПМ210/других шлюзов. При этом наличие Modbus не объявляется автоматически механизмом загрузки пользовательской программы.

## Что осталось

1. Реальная протокольная идентификация endpoint'ов.
2. Пользовательский экран обнаружения.
3. Отображение совпадений профилей и уровня уверенности.
4. Явное подтверждение привязки к объекту проекта.
5. Реальные transport/deployment adapters только для подтверждённых операций записи.

## Следующий шаг

Сначала реализовать протокольную идентификацию и UI обнаружения, затем подключить адаптеры передачи. До этого не объявлять неподтверждённые способы программирования как готовую функцию.

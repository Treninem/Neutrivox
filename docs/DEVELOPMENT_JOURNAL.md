# Журнал разработки Neutrivox

Этот файл является постоянным журналом проекта. После каждого значимого этапа сюда добавляются: что сделано, что проверено, планы, проблемы и причины решений.

---

## 2026-08-27 — Большой этап: единое рабочее пространство и безопасный путь к реальному оборудованию

### Что сделано
- Добавлен сервис единого рабочего пространства проекта с подсчётом устройств, каналов, ошибок и предупреждений.
- Добавлена явная система привязки объекта проекта к физически обнаруженному устройству только после подтверждения пользователя.
- Добавлена предварительная проверка перед загрузкой: ошибки проекта, наличие выбранных устройств и их сопоставление с физическими целями.
- Добавлена основа журнала действий проекта для последующего отображения истории изменений и операций.
- Добавлена подробная инструкция единого процесса работы: от проектирования и симуляции до проверки и поочерёдной передачи.

### Что изменилось
Архитектура теперь связывает ранее созданные части в один последовательный рабочий процесс. Цифровой проект не отделяется от физического: подключение оборудования добавляет подтверждённую связь с теми же объектами проекта.

### Что проверено
Новые проверки являются предварительными и не выполняют запись в оборудование. Сопоставление требует явного подтверждения, а отсутствие привязки блокирует готовность выбранного устройства к загрузке.

### Какие проблемы обнаружены
Интерфейс необходимо крупным этапом перестроить вокруг единого рабочего пространства, чтобы новые возможности были доступны пользователю, а не только существовали в сервисах.

### Какое решение принято и почему
Перед реализацией реальных адаптеров загрузки выбран строгий этап предварительной проверки. Это уменьшает риск отправки конфигурации не в тот объект и позволяет добавлять поддержку разных производителей через отдельные проверенные адаптеры.

### Что делать дальше
1. Перенести рабочее пространство, статусы и предварительные проверки в интерфейс.
2. Создать полноценное визуальное поле проекта и свойства выбранного объекта.
3. Подключить редактор логики и симулятор к интерфейсу.
4. Добавить автоматические тесты и CI-проверку расширенных сервисов.
5. После проверки официальных данных реализовать реальные профили и адаптеры конкретных приборов.

## 2026-08-29 — Большой этап: компиляционная стабилизация и унификация контрактов

### Что сделано
- Устранены несовместимости deployment-моделей, возникшие после добавления последовательной физической передачи.
- Унифицированы состояния deployment: неподдержанный адаптер больше не выдаётся за отдельное несуществующее состояние.
- Исправлен readiness-report: теперь он создаётся по действительной модели `ProjectReadinessReport` и заполняется через `Items`.
- Удалён конфликтующий второй `LicenseState`: политики лицензирования используют канонические `ProductEdition` и `LicenseState` из `Neutrivox.Models`.
- Добавлена фабрика `SimulationTraceService.Create()`, используемая UI и сценариями симуляции.
- Исправлен вызов создания связи в основном интерфейсе под фактический контракт `ProjectConnectionService`.
- Исправлена выпускная проверка проекта: она использует `BuildSnapshot()`, существующие диагностические результаты и реальное свойство готовности симуляции.
- Сохранён единый проектный workflow без разделения на отдельные режимы «с прибором» и «без прибора».

### Что проверено
- Последние CI-прогоны дошли до реальной компиляции и показали конкретные несовместимости сервисных типов.
- После исправлений ошибок UI были устранены отдельные проблемы `ProjectStatusText`, `readonly` discovery coordinator и неподдерживаемого свойства `Grid.ColumnSpacing`.
- Новый проход унификации readiness/validation/binding выполнен через канонические модели `Neutrivox.Models`.

### Какие проблемы обнаружены
Было выявлено затенение канонических моделей одноимёнными типами в пространстве имён `Neutrivox.Services`. Из-за этого один и тот же символ `ValidationSeverity`, `ProjectReadinessReport` или `PhysicalDeviceBinding` разрешался в разные типы и ломал компиляцию.

### Какое решение принято и почему
Не добавлять очередные адаптеры между дубликатами, а выбрать один источник истины — модели проекта в `Neutrivox.Models`. Readiness, validation, preflight и physical binding теперь должны использовать именно эти модели. Это одновременно уменьшает количество разделов/дублей и делает дальнейшую интеграцию UI и deployment предсказуемой.

### Что сделано в текущем проходе
- `ProjectReadinessService` переведён на канонический `Neutrivox.Models.ProjectReadinessReport`; локальный дубликат readiness-report удалён из сервисного контракта.
- `DeploymentReadinessService` дополнен поверх канонического readiness-report и больше не создаёт собственный тип отчёта.
- `ProjectValidationService` использует канонический `Neutrivox.Models.ValidationSeverity`.
- `UnifiedProjectWorkspaceService` использует тот же канонический severity.
- `DeploymentPreflightService` использует канонический severity и явно показывает номер цели в последовательном плане.
- `ProjectMappingService` и `ProjectBindingService` явно создают `Neutrivox.Models.PhysicalDeviceBinding`, исключая разрешение к одноимённому сервисному типу.
- `ReleaseReadinessService` переведён с устаревшего `IsReadyForSimulation` на канонический `CanSimulate`.

### Следующий контрольный блок — устранение последнего подтверждённого compile-блокера
Последний доступный CI-run (`Build Neutrivox #335`, commit `4a643a5...`) завершился на этапе `Build application` с единственной ошибкой: `ProjectHealthService` обращался к старому свойству `ProjectReadinessReport.Checks`, тогда как каноническая модель содержит `Items`.

Причина выбора исправления: после унификации readiness нельзя возвращать локальную копию отчёта только ради совместимости одного сервиса. `ProjectHealthService` должен следовать единой канонической модели.

### Что сделано
- `ProjectHealthService` переведён с устаревшего `.Checks` на канонический `.Items`.
- Логика преобразования уровней readiness теперь напрямую использует `ProjectReadinessLevel`.
- Сохранена пользовательская health-модель сервиса без добавления второго readiness-контракта.

## 2026-08-30 — Release Candidate и подготовка загрузочника

### Что сделано
- Исправлена сериализация проекта: коллекции устройств, каналов, связей и тегов получили settable-свойства, чтобы JSON round-trip мог восстановить полную структуру проекта.
- Усилен Smoke Test: он проверяет не только наличие устройства после загрузки, но и сохранение идентификаторов устройства и каналов.
- Получен полностью зелёный CI: `Build application`, `Build smoke test` и `Run smoke test` завершились успешно.
- Windows Package Check прошёл полный путь: restore, Release build, smoke, Windows x64 publish, проверку `Neutrivox.exe` и компиляцию Inno Setup.
- Добавлены `README_RU.md`, `README_EN.md`, `VERSION.txt` и `CHANGELOG.md` для релизного комплекта.
- Windows Release workflow дополнен проверками документации, версии, опубликованного EXE, установщика, ZIP и SHA-256.
- Windows Release workflow переведён на запуск также от push в `main`, чтобы можно было автоматически проверить реальный артефакт без ручного запуска через интерфейс GitHub.
- Установщик переведён на версию из `VERSION.txt` через `/DMyAppVersion`, а документация включена в установленный пакет.

### Какие проблемы были обнаружены
1. После первой успешной компиляции Smoke Test обнаружил реальную потерю устройств при JSON round-trip.
2. Старый Release workflow создавал пакет, но предыдущая проверка не давала доступного сохранённого artifact.
3. Версия установщика была жёстко задана внутри `.iss`, что могло привести к несовпадению версии установщика и `VERSION.txt`.

### Какое решение принято и почему
Ошибки не маскируются ослаблением тестов. Исправляется причина потери данных в модели, а релизный workflow должен проверять не только компиляцию, но и наличие конечных файлов. Версия берётся из одного источника — `VERSION.txt`, чтобы исключить рассинхронизацию.

### Что проверено
- Основной Build: успешно.
- Smoke Build: успешно.
- Smoke Runtime: успешно.
- Windows x64 publish: успешно.
- Inno Setup compile: успешно.

### Что сделано для финального загрузочника
Добавлена автоматическая выдача релизного artifact с:
- Windows x64 ZIP;
- `Neutrivox-Setup-<version>.exe`;
- `SHA256SUMS.txt`;
- документами релиза внутри Windows-пакета.

### Ограничение текущей проверки
GitHub connector не предоставляет отдельную операцию `workflow_dispatch`, поэтому для получения реального финального artifact Release workflow был переведён на автоматический запуск при push в `main`. До завершения этого нового запуска нельзя объявлять загруженный установщик физически доступным в текущем чате.

### Что делать дальше
1. Получить результат нового Windows Release run после изменений.
2. Проверить наличие и содержимое artifact.
3. Скачать artifact через GitHub Actions и проверить его целостность.
4. После успешной проверки выдать пользователю реальный загрузочный файл, а не ссылку на исходники.
5. Только после этого объявить первый релиз Neutrivox готовым.

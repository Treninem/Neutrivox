# Рабочая запись — wiring физической передачи и QA

## Что проверено
- `DeploymentExecutionService` уже требует явный `confirmedByUser` и выполняет цели по `DeploymentTarget.Order`.
- Перед первым физическим I/O выполняются проверка fingerprint и `DeploymentSafetyGateService`.
- Перед каждой следующей целью fingerprint проверяется снова.
- Отсутствие проверенного adapter останавливает последовательность.

## Как понято требование пользователя
Neutrivox должен не просто хранить архитектуру передачи, а иметь единый понятный путь от плана до конкретного физического прибора. Поэтому все проверки должны быть частью одного execution path, а не разрозненными кнопками.

## Почему выбрано это решение
Промышленная конфигурация не должна отправляться по устаревшему плану. Повторная проверка перед каждым прибором уменьшает риск изменения проекта между операциями последовательной передачи. Явный порядок исключает скрытую сортировку по техническому идентификатору.

## Следующий крупный блок
1. Проверить и интегрировать все вызовы `DeploymentExecutionService` после изменения сигнатуры.
2. Добавить regression-тесты на неверный Order, другой ProjectId, отсутствие fingerprint, устаревший fingerprint, отсутствие adapter и успешную последовательность.
3. Подключить этот execution path к конечному UI вместо отдельных демонстрационных действий.
4. После этого провести полный compile/regression и уже только затем собирать Windows Release.

## Статус
Execution core усилен; UI и полный regression остаются обязательными до релиза.

# Рабочая запись: последовательное выполнение передачи

## Пользовательское сообщение
«продолжи».

## Как понято
Нужно продолжить разработку крупным функциональным блоком. Предыдущее ядро уже умеет строить план, проверять безопасность и выбирать адаптер. Следующим логичным слоем является фактический оркестратор, который запускает выбранные цели строго по очереди и даёт пользователю результат по каждому прибору.

## Что сделано

1. Добавлен `DeploymentExecutionService`.
2. Выполнение идёт строго по одному target за раз.
3. Перед запуском адаптера проверяется наличие контекста и явного подтверждения пользователя.
4. Если для профиля нет зарегистрированного адаптера, устройство не объявляется успешно загруженным — оно получает `Skipped`.
5. При ошибке одного прибора последовательность останавливается, чтобы не продолжать массовую операцию при неизвестном состоянии предыдущего шага.
6. Добавлен `DeploymentAuditService` для последовательной истории операций текущего плана.
7. Добавлен `DeploymentReportService` для понятного текстового итогового отчёта.
8. Добавлен отдельный документ с результатами этого блока.

## Почему выбран такой вариант

Требование владельца проекта — передавать не сразу во все приборы, а по очереди с пониманием, что именно и куда загружается. Поэтому последовательность является отдельным объектом управления. Реальный I/O остаётся внутри конкретного проверенного адаптера; оркестратор не знает закрытых деталей протокола.

Отдельный аудит нужен для диагностики и последующего пользовательского отчёта. При отсутствии адаптера лучше явно пропустить цель, чем выдавать фиктивный успех.

## Важное ограничение

Этот блок не заявляет, что программа уже умеет программировать любую конкретную модель. Адаптер должен отдельно реализовать и подтвердить физический протокол передачи.

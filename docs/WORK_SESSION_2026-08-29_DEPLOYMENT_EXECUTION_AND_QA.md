# Рабочая сессия — deployment execution и QA

## Запрос пользователя
Пользователь попросил продолжить разработку. Основное действующее правило процесса: делать максимально крупные связанные изменения, не выдавать незаписанные изменения за выполненные и после окончания провести полную проверку.

## Что проверено
- `DeploymentTarget` должен хранить явный порядок, потому что порядок передачи является пользовательским решением проекта.
- `DeploymentExecutionService` должен использовать этот порядок, а не сортировку GUID.
- `DeploymentPlanFingerprintService` и `DeploymentPlanGuardService` уже существуют и предназначены для обнаружения устаревшего плана.
- `DeploymentSafetyGateService` блокирует физическую передачу без явного подтверждения, проверенного профиля и deployment adapter.

## Решение
Следующий production-путь должен быть последовательным и проверяемым:

`подготовить план -> fingerprint -> preflight -> safety gate -> передача цели №1 -> результат -> цель №2 -> результат -> ...`

При изменении проекта между подготовкой и физической операцией старый план использовать нельзя.

## QA-правила
1. Порядок целей не должен вычисляться по случайному идентификатору.
2. Пропущенная цель или несогласованный порядок блокирует выполнение.
3. Отсутствие explicit confirmation блокирует физическую операцию.
4. Отсутствие verified read/write adapter блокирует конкретную цель.
5. При неуспешной физической операции дальнейшие цели автоматически не запускаются.
6. Наличие модели в каталоге или успешного discovery само по себе не доказывает возможность записи.
7. Финальным считается только фактически собранный и проверенный Windows пакет.

## Что осталось
- Интегрировать guard непосредственно перед физическим execution.
- Подключить deployment UI к новому порядку и состояниям.
- Провести фактический compile/regression и исправить найденные ошибки.
- После зелёной проверки собрать Windows publish и установщик.

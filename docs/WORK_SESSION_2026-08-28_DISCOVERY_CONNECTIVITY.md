# Рабочая запись: обнаружение, связь и идентификация — продолжение

## Сообщение пользователя, с которого начат блок

Пользователь попросил продолжить разработку и одновременно показывать, сколько крупных этапов осталось и за какое ориентировочное количество ответов можно закончить.

## Как понято

Нужно продолжать разработку в репозитории крупными связанными блоками и показывать реальный остаток работ. Оценка числа ответов является ориентиром, а не гарантией: крупный блок может выявить ошибки и потребовать дополнительной переработки.

## Что сделано

Сверена существующая архитектура discovery: поиск выполняется через зарегистрированные providers и не считает IP доказательством модели. Сверены профили ОВЕН и границы заявленной поддержки: точные варианты ПР100 и ПМ210 профилируются, но программная загрузка пока не объявлена готовой возможностью. Продолжено разделение endpoint validation, discovery, identification и binding, чтобы транспортная логика не смешивалась с UI. Продолжен CI/smoke-контур для контроля базового сценария симуляции, сохранения, endpoint validation и регистрации профилей.

## Почему выбран этот вариант

Для реального распознавания подключённого прибора одной проверки IP недостаточно. Нужна последовательность endpoint → транспорт → ответ устройства → признаки идентификации → подходящий профиль → кандидат сопоставления. Каждый слой должен быть отдельно проверяемым.

## Ограничение

Наличие Modbus или другого транспорта само по себе не доказывает возможность загрузки пользовательской программы контроллера. Загрузка будет считаться поддержанной только после отдельной проверки документированного механизма передачи и тестирования.

## Следующий крупный блок

Завершить UI обнаружения и сопоставления, затем перейти к полноценным подтверждённым транспортным адаптерам и далее к безопасной последовательной передаче.

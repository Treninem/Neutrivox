# Рабочая запись — порядок deployment и QA

## Запрос пользователя
«далее».

## Как понят запрос
Продолжить разработку непосредственно в репозитории и не ограничиваться описанием планов. Следующим крупным техническим блоком должен быть переход от архитектурной подготовки deployment к проверяемому пользовательскому workflow и контролю качества.

## Что проверено перед изменениями
- `DeploymentWorkflowService` уже формирует пользовательские элементы с порядковым номером.
- `DeploymentExecutionService` ранее сортировал `DeploymentPlan.Targets` по `ProjectDeviceId`, из-за чего порядок мог отличаться от порядка, показанного пользователю.
- `DeploymentPlanFingerprintService` уже защищает от использования устаревшего плана.
- `DeploymentSafetyGateService` уже требует явного подтверждения и verified read/write adapter.

## Решение
Порядок передачи должен быть частью самой модели `DeploymentTarget`, а не вычисляться сортировкой GUID. GUID нельзя использовать как пользовательский порядок.

Также финальная UI-передача должна проходить только через последовательность:
1. построить plan;
2. зафиксировать fingerprint;
3. повторно проверить fingerprint непосредственно перед физической операцией;
4. проверить safety gate;
5. выполнить target 1;
6. записать результат;
7. только после этого перейти к target 2 и далее.

При ошибке передача следующих целей не должна происходить автоматически.

## Почему
Пользователь прямо потребовал понимать, какой проект и куда загружается, и передавать приборы по очереди. Явный order обеспечивает одинаковое отображение и выполнение. Повторная проверка fingerprint исключает тихое использование изменённого проекта. Остановка после ошибки уменьшает риск продолжить цепочку с неизвестным состоянием предыдущего устройства.

## QA
До объявления релиза нужно проверить:
- порядок 1..N;
- stale-plan rejection;
- отсутствие физической операции без явного confirmation;
- блокировку unsupported/read-only профиля;
- остановку последовательности после неуспешного target;
- отсутствие ложного успеха при ошибке внешней утилиты;
- RU/EN сообщения;
- smoke/regression и Release build.

## Следующее
Интегрировать order и guard в execution path, затем провести фактическую сборку и regression. Не считать релиз готовым до успешной проверки.

# Рабочая запись: единый рабочий экран и подготовка передачи

## Пользовательское сообщение
«далее».

## Как понято
Продолжить фактическую разработку, не создавая новые независимые разделы для виртуальной и физической работы. Следующий слой должен объединять уже существующие сервисы в общий рабочий сценарий.

## Что сделано

1. Добавлен `UnifiedProjectWorkspaceService`, который создаёт единое представление проекта: оборудование, I/O, связи, логические сети, инструкции, ошибки и предупреждения проверки.
2. Добавлен `ProjectWorkspaceDiagnosticsFacade`, чтобы будущий UI обновлял состояние проекта одним вызовом и не дублировал правила проверки в разных экранах.
3. Добавлен `DeploymentPlanFormatter`, который превращает подготовленный план передачи в понятный человеку RU/EN отчёт без выполнения передачи.

## Почему выбран такой вариант

Текущий UI ранее содержал отдельные простые экраны и часть backend-функций уже существовала. Дописывать ещё один самостоятельный экран было бы созданием дублирующего состояния. Поэтому сначала создаётся единый read-model/facade слой, который позволит подключить интерфейс к существующему ядру без копирования бизнес-правил.

Отдельный форматтер плана передачи нужен потому, что оператору необходимо увидеть именно то устройство и endpoint, с которым будет работать операция, до подтверждения. Планирование и реальная передача остаются различными действиями.

## Что это меняет

Теперь основной UI может показывать один сводный статус проекта и один человекочитаемый предпросмотр будущей передачи, используя существующее ядро проекта.

## Что ещё требуется

- подключить фасады к MainWindow и заменить демонстрационные/заглушечные представления рабочими данными;
- сделать полноценный редактор логики;
- завершить UI обнаружения и сопоставления устройств;
- подключить подтверждённые адаптеры реального оборудования;
- реализовать последовательный deployment поверх подготовленного плана;
- завершить RU/EN, лицензирование, тесты и выпуск.

## Проверка

Изменения добавлены отдельными коммитами. Автоматическая проверка репозитория должна подтвердить совместимость новых классов с текущей архитектурой; неподтверждённые результаты сборки не выдаются за успешные.

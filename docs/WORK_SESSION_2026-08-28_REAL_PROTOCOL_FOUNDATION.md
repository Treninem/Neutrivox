# Рабочая запись: реальный протокол и интерфейсы связи

## Пользовательское сообщение
«далее».

## Как понята задача
Следующим крупным блоком требуется перейти от абстрактных контрактов связи к реальной технической основе, но не выдавать каркас за готовую загрузку программы в конкретный контроллер.

## Что сделано

1. Проверена официальная документация ОВЕН по ПР100. Она подтверждает среду Owen Logic, программирование через micro USB и наличие RS-485 с Modbus RTU/ASCII у соответствующих модификаций.
2. Добавлен `ModbusRtuFrameService` с построением стандартных запросов чтения/записи регистров и проверкой CRC16.
3. Добавлен `SerialPortInventoryService` для получения доступных COM-портов на машине пользователя.
4. Профили ОВЕН остаются разделены по уровню: знание модели не означает автоматически наличие проверенного механизма загрузки программы.
5. Для ПМ210 сохранена отдельная роль сетевого шлюза: профиль не объявляет его конечным загрузчиком программы контроллера.

## Почему выбран такой вариант

Официальная документация ПР100 прямо описывает micro USB как интерфейс программирования и указывает Owen Logic как среду программирования. Поэтому нельзя честно реализовывать «загрузку программы по Ethernet/Modbus» только потому, что в системе присутствует Modbus.

Modbus RTU имеет смысл сначала реализовать как транспортный строитель/валидатор кадров для задач чтения и записи документированных регистров. Драйвер конкретной загрузки программы требует отдельного исследования и тестирования по документации Owen Logic и конкретного устройства.

## Что дальше

1. Подключить перечисление COM/RS-485 к UI обнаружения.
2. Добавить Ethernet endpoint inventory без ложного утверждения, что каждое найденное TCP-устройство является ОВЕН.
3. Сделать реальные профильные проверки для конкретных модификаций.
4. Реализовать безопасный адаптер передачи только после подтверждения документированного способа загрузки и проверки на целевом оборудовании.
